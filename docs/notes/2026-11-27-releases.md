# Ready-made builds on every merge, and a double-click start

Players without Rust or git can now download a built `leonida.exe` and double-click it.

## The Release workflow

`.github/workflows/release.yml` runs after CI passes on a push to `main`. Its `build` job runs
`cargo build --release --locked -p leonida` on `windows-latest` with a static C runtime
(`-C target-feature=+crt-static`), so the exe starts on a PC without the Visual C++
Redistributable, and fails if `dumpbin /dependents` still lists `VCRUNTIME140.dll` or an
`api-ms-win-crt` DLL. The zip, `leonida-windows-x64.zip`, holds a `leonida` folder with
`leonida.exe`, `LICENSE`, `leonida.example.toml`, `THIRD-PARTY-LICENSES.txt` (the licence files of
every crate built into the exe, from `scripts/third-party-licenses.ps1`), `version.txt` (`build=`,
`commit=`, `source=`, the last a link to the source of that commit, as the GPL asks) and a
`README.txt` telling players to double-click `leonida.exe`.

The `build` job has a read-only token and checkout keeps no token in `.git/config`, since build
scripts and proc macros run there. A separate `publish` job, the only one with a write token,
checks nothing out: it downloads the zip and publishes the GitHub release "Build <n>" with the tag
`build-<n>`. A build number that is out already on the same commit is skipped, so a rerun publishes
nothing twice; on another commit (a rewritten `main`) the job fails. A build older than the newest
one published is not marked Latest. Runs that may publish wait for each other; GitHub keeps one
waiting run, so a burst of merges can skip a build number but never publish one twice.

A pull request that changes the workflow or the licence script, or a run started by hand, builds
the zip as an artifact and publishes nothing. To publish a build again, re-run its run from the
Actions page: that keeps the check that CI passed.

## The build number

`<n>` is `git rev-list --count` of the commit: the number of commits up to it. It only grows along
`main`, needs no counter stored anywhere, and anyone with a checkout can work out the same number
for the same commit, so a local build and a release can be compared without asking GitHub. The
workflow sets `RELEASE_BUILD_NUMBER` and `RELEASE_BUILD_COMMIT` for the build; `leonida version`
prints them as `version=`, `build=` and `commit=` lines, or `local` for any other build.
`apps/leonida/build.rs` marks both variables so a cached build picks up a new number. The launcher
(a separate repository) will compare its local build number with the newest `build-<n>` release
and show that an update exists; it never updates by itself. Until it ships, the README tells
players to look for a higher Build number on the Releases page.

## Double-click mode

`leonida` with no command, started in a console (as a double-click does), now does what
`run-gta6.ps1` does after its build step. With no console input (a script, an agent, a launcher)
it prints the usage and exits with code 2, as before; every other command behaves as before.

It first moves to the exe's folder when `LEONIDA_CONFIG` is unset and the current folder has no
`leonida.toml`, so a start from the Run dialog or a launcher finds and saves the same file as a
double-click, and it warns when the exe runs from `%TEMP%` (opened inside the zip). It uses the
configured game folder if it has a `MicrosoftGame.config`, else the last one used by this or a
later build (`%LOCALAPPDATA%\leonida\game-folder.txt`, so a new zip needs no setup), else searches
(`XboxGames\*\Content` and the top two folder levels of each drive, Downloads and Desktop, for a
manifest with the game's title id) and offers what it finds, else asks for one (it can be dragged
into the window). The folder chosen is saved to `leonida.toml` and remembered. The search runs a
thread for each drive, so a slow or offline drive holds up only itself, and stops after 2 seconds,
or 6 while it has found nothing, or 2000 folders a drive. Mapped network drives are searched too:
skipping them needs `GetDriveTypeW`, a `windows-sys` feature this crate does not enable yet. It
offers the shader warm-up with the script's wording ([Y/n], Enter is yes), sets `LEONIDA_LOG=warn`
when it is unset and starts the game. The warm-up and the game run as
`leonida translate --warm all` and `leonida run --execute` children in the same window: the same
paths as from the script, a title that relaunches itself gets a command line it can reuse, and a
crash still leaves the parent to say what happened and wait for Enter.

Once the children start, the parent ignores Ctrl+C and Ctrl+Break with a handler of its own (not
`SetConsoleCtrlHandler(None, TRUE)`, which children would inherit), so Ctrl+C ends only the warm-up
or the game and the window says it was stopped with Ctrl+C. A stopped warm-up starts the game
anyway. Before the final "Press Enter" it empties the console's input buffer, so Enter presses made
during the warm-up or the game don't close the window at once.

Not handled: a title relaunch (`XLaunchNewGame`, untested live) ends the first child, so the window
says the game has closed while the relaunched one starts. Waiting on a Job object would fix it, but
it needs the relaunch to be tested in game first.

## Measured

Nothing in game: this changes how the program is built and started, not what it does once the
title runs. The unit tests cover the argument parsing, the version lines, the warm-up answer and
the game folder search on a temporary folder tree; the search has not been timed on real drives. A
local release build with the static C runtime was checked with `dumpbin /dependents`, and the
licence script was run on Windows PowerShell 5.1. The workflow itself has not run yet.
